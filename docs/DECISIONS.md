# DECISIONS.md — зафіксовані рішення

Кожне рішення тут — це відповідь на питання, яке інакше довелося б приймати
тричі по-різному. Формат: **рішення → чому → як пояснити на співбесіді**.

Статус: усі пункти **ЗАФІКСОВАНО**. Змінювати можна, але тоді треба оновити
`data-model.md` і, можливо, міграцію.

# A. Стек

## A1. Next.js 15 App Router як full-stack, без окремого backend

**Рішення:** один Next.js-застосунок. Route Handlers (`app/api/**/route.ts`) —
це справжні HTTP-ендпоінти; Server Components — серверний код із доступом до БД.

**Чому:** окремий NestJS для трьох екранів — це два деплої, CORS, ручна
синхронізація типів між репо. Користі нуль, накладних витрат багато.

**На співбесіді:**
> «Next.js App Router — повноцінний full-stack фреймворк: Route Handlers дають
> справжній REST, типи спільні автоматично. Архітектуру я побудував пошарово,
> тому якщо проєкт виросте — сервісний шар переїжджає в Nest без переписування
> бізнес-логіки, зміниться тільки транспорт.»

## A2. Три шари, логіка тільки в сервісах

```
Route Handler (/api/orders)  ─┐
                              ├─→  orders.service.ts  ─→  Prisma  ─→  Postgres
Server Component (page.tsx)  ─┘      (вся бізнес-логіка)
```

**Рішення:** Server Components викликають сервіс **напряму**, без HTTP-запиту до
власного API. Клієнтські взаємодії (фільтри, пагінація, перемикач вигляду) —
через REST.

**Чому:** запит застосунку до самого себе по HTTP — зайвий мережевий хоп і
повільніший TTFB. Але REST потрібен і за умовою завдання, і для клієнтських
взаємодій. Спільний сервіс = немає дублювання.

**На співбесіді:**
> «REST API покриває всі дані — можна відкрити `/api/orders?hub=markham` у
> браузері. Але SSR-сторінки не роблять HTTP-запит самі до себе: вони викликають
> той самий сервісний шар напряму. Логіка одна.»

## A3. PostgreSQL на Supabase, підключення через Prisma

**Рішення:** керований Postgres від Supabase, звичайне Prisma-підключення.
Supabase SDK, Auth, Storage і Realtime **не використовуються**.

**Чому:** Postgres обов'язковий за умовою. Supabase — знайомий інструмент, є
вбудований SQL Editor (стане в пригоді на демо). Відсутність їхнього SDK означає
відсутність vendor lock-in.

**На співбесіді (це питання поставлять):**
> «Мені потрібен був керований Postgres. Підключаюсь звичайним Prisma, без їхнього
> SDK — тому міграція на будь-який інший Postgres це один рядок в env. Решту
> сервісів не використовую свідомо. Якби додавав авторизацію і зберігання фото —
> Supabase Auth і Storage закрили б це без окремої інфраструктури.»

## A4. Prisma як ORM, але агрегації — сирим SQL

**Рішення:** Prisma для CRUD і фільтрів. Тижнева агрегація для графіків —
`$queryRaw` з `date_trunc('week', ...)` і `GROUP BY`.

**Чому:** типобезпека наскрізна (змінив колонку → TypeScript підсвітив усе), і
міграції лежать у git. Але тягнути 72 рядки в Node і рахувати `reduce` — це
антипатерн, який на 100k рядків розвалиться.

**На співбесіді:**
> «ORM закриває 90% запитів. Агрегацію по тижнях зробив raw SQL із `date_trunc` —
> один запит до бази замість вивантаження рядків у Node. ORM — інструмент, а не
> заміна SQL.»

## A5. Стан фільтрів — в URL, не в React-стейті

**Рішення:** `/orders?tab=alerts&hub=markham&page=2`. Читається через
`searchParams` у Server Component, валідується zod, іде в `where` для Prisma.

**Чому:** фільтрація на клієнті означає віддати всі рядки на клієнт (не
масштабується), і стан гине після F5.

**На співбесіді:**
> «URL — найпростіший стейт-менеджер, який уже є в браузері: стан шериться
> посиланням і виживає перезавантаження, а фільтрація відбувається в базі.»

## A6. Recharts для графіків

**Рішення:** Recharts.
**Чому:** декларативний React-API, нормально працює з App Router (обгортка
`"use client"`). Chart.js теж підійшов би — це імперативний canvas-API, потребує
`useRef` + ручного знищення інстансу. Для двох простих графіків Recharts коротший.

# B. Домен: суперечності макета і як вони розв'язані

> ⚠️ Це найважливіша секція. Три числа в макеті між собою не сходяться — це
> нормально для wireframe, але реалізувати «як намальовано» неможливо. Нижче —
> узгоджена модель.

## B1. Таби — взаємовиключні сегменти

**Проблема:** у макеті `All 27 · Cross-Dock 18 · Consolidation 6 · Alerts 2 · Drafts 1`.
Але 18 + 6 + 1 = 25 ≠ 27. Якщо таби перетинаються — сума не має сходитись узагалі;
якщо не перетинаються — має дорівнювати 27.

**Рішення:** таби взаємовиключні, ордер потрапляє рівно в один. Пріоритет:

```
1. status === DRAFT           → Drafts
2. hasAlert === true          → Alerts
3. type === CROSS_DOCK        → Cross-Dock
4. type === CONSOLIDATION     → Consolidation
```

Перевірка: 1 + 2 + 18 + 6 = **27** ✅

**Чому:** сума лічильників дорівнює `All` — це те, чого очікує користувач.
Ордер з алертом важливіший за свій тип, тому Alerts перехоплює раніше.

**На співбесіді:**
> «У макеті лічильники табів не сходились із загальною кількістю. Я зробив таби
> взаємовиключними сегментами з пріоритетом Draft → Alert → тип, тоді сума
> сходиться з All. Це рішення, а не збіг — воно задокументоване.»

## B2. Взаємодія табів і фільтрів — AND

**Рішення:** таб і фільтри Hub/Date/Status застосовуються разом через `AND`.
`?tab=alerts&hub=markham` = ордери з алертом у Markham.

**Виняток:** таб `Drafts` ігнорує фільтр `Status` (у чернетки немає осмисленого
статусу) — фільтр рендериться задизейбленим.

**Лічильники табів рахуються з урахуванням Hub і Date, але БЕЗ урахування
поточного табу.** Тобто перемикання Hub оновлює всі цифри на табах; перемикання
табу — ні.

## B3. `Alert` — це прапорець, а не статус

**Проблема:** у макеті `FR001674` має бейдж `Alert`, але при цьому це
`Consolidation` у роботі. Якщо `Alert` покласти в `status`, ми втратимо
інформацію про реальний стан ордера.

**Рішення:** `hasAlert: Boolean` + `alertMessage: String?` окремо від `status`.
На картці бейдж алерта **замінює** бейдж статусу (бо він важливіший), бейдж типу
лишається.

## B4. Два набори статусів: pipeline vs label

**Проблема:** у макеті flow `Draft → Ready → In Progress → Consolidated →
In Transit → Deconsolidated → Closed` (7 станів), а на картках бейджі
`New`, `In progress`, `Alert`, `Completed`, `Draft`, `On Stock` (інший набір).

**Рішення:** у БД — enum із 7 pipeline-статусів (джерело правди). Лейбл для UI —
**похідна функція** від `(status, type)`:

| status | type | label на бейджі |
|---|---|---|
| `DRAFT` | будь-який | `Draft` |
| `READY` | будь-який | `New` |
| `IN_PROGRESS` | `CROSS_DOCK` | `On Stock` |
| `IN_PROGRESS` | `CONSOLIDATION` | `In progress` |
| `CONSOLIDATED` | — | `Consolidated` |
| `IN_TRANSIT` | — | `In transit` |
| `DECONSOLIDATED` | — | `Deconsolidated` |
| `CLOSED` | — | `Completed` |

Плюс правило понад таблицею: `hasAlert === true` → бейдж `Alert` (варіант
`danger`), незалежно від статусу.

**Чому:** у БД зберігаємо стан, а не текст. Лейбл — представлення, він живе в
`lib/status.ts` і покритий юніт-тестом.

## B5. `Need Attention: 3` — розкладка

**Проблема:** макет каже `3 Total = 2 · awaiting your action + 1 · alert`, але
таб `Alerts` каже `2`. Одне з двох чисел неправильне.

**Рішення:** `hasAlert = 2`, `awaitingClientAction = 1`, разом `3`.
Тобто **два числа в розкладці на дашборді міняються місцями** порівняно з
макетом: рендеримо `2 · alert` + `1 · awaiting your action`.

**Чому:** таб `Alerts = 2` бере участь у сумі 27 (див. B1), тому це число
жорсткіше зафіксоване. Розкладка на дашборді — просто підпис.

`awaitingClientAction: Boolean` — окреме поле в БД (вивести його з інших даних
неможливо: «клієнт має щось зробити» це бізнес-подія, а не наслідок статусу).

**Простежуваність.** До ревʼю це поле рахувалось лише в `needAttention` і ніде більше
не потрапляло в UI: не було в `OrderListItemDTO`/`OrderDetailDTO`, не мало бейджа на
картці/деталі, а `breakdown[].detail` для цього рядка завжди повертав `null` (на
відміну від alert, де є `representativeAlert`) — «1 · awaiting your action» на
дашборді фізично не можна було простежити до конкретного ордера. Виправлено:
`awaitingClientAction` тепер у DTO обох рівнів, є `AwaitingActionBadge` на
`OrderCard`/`OrdersTable`/`OrderDetailHeader`, і `breakdown` несе `orderNumber`
представника (як і alert) — чіп на дашборді веде на `/orders?search=<number>`,
через уже наявний пошук по `number`, без нового фільтра чи табу.

**Про вікно часу:** `needAttention` на дашборді рахується по **всій базі**, без
30-денного обмеження — на відміну від таба `Alerts` в Order List, де воно є
(`period` за замовчуванням `last-30-days`, DECISIONS.md A5). Це свідомо: «потребує
уваги» — стан, не запис за проміжок, і не повинен залежати від фільтра періоду в
іншому розділі застосунку. На поточному сіді числа збігаються, бо всі
`hasAlert=true` лежать в останні 30 днів (`data-model.md` §2.4) — але це властивість
даних, не гарантія API.

**Чернетки не рахуються.** Вікно часу — **єдина** навмисна розбіжність із табом `Alerts`.
За пріоритетом табів (B1) чернетка завжди належить до `Drafts`, ніколи до `Alerts`, тож
`needAttention` теж виключає `status = DRAFT`. Інакше KPI показував би `N`, а список, на
який користувач переходить кліком, — `N−1`. Один запит у `dashboard.service.ts` і
`countNeedAttention` у seed написані однаково саме для цього.

## B6. `Active Orders` — які статуси вважаються активними

**Рішення:** активний = `status IN (READY, IN_PROGRESS, CONSOLIDATED, IN_TRANSIT,
DECONSOLIDATED)`. Тобто **все, крім `DRAFT` і `CLOSED`**.

Тренд `▲ 2 this week` = кількість активних ордерів, у яких `createdAt` у поточному
ISO-тижні. Не різниця з минулим тижнем — так простіше і чесніше рахується.

## B7. `Completed (30 d)` рахується по `closedAt`, а не по `scheduledAt`

**Проблема:** `Active 7` + `Completed 24` = 31 > `All 27`. Виглядає як помилка.

**Рішення:** це **різні поля і різні вибірки**:
- фільтр `Date` в Order List фільтрує по `scheduledAt` (коли ордер запланований);
- KPI `Completed (30d)` рахує по `closedAt` (коли фактично закрито).

Ордер, запланований 45 днів тому, а закритий 5 днів тому, потрапляє в KPI, але
не в список за останні 30 днів. Суперечності немає.

**На співбесіді:** це хороша відповідь на «а чому 7 + 24 більше за 27?» — питання
цілком можуть поставити, і готова відповідь виглядає сильно.

## B8. Тренди й інсайти рахуються, а не хардкодяться

У макеті `same as last month` і `+18% completed orders vs previous month` —
суперечать одне одному (не може бути «так само» і «+18%» одночасно).

**Рішення:** обидва рядки — обчислювані. Seed задає `24` завершені за останні
30 днів і `20` за попередні 30 → застосунок покаже `+20%`. Текст у макеті —
плейсхолдер.

**Ділення на нуль.** Якщо попередній період порожній, відсоткової зміни математично не
існує. Конвенція (`lib/format.ts::computeTrendPercent`, покрита тестом): `0 → 0` дає `0`
(«flat»), `0 → будь-що` дає `100` («up»); ніколи `Infinity` чи `NaN`, бо KPI-картка вміє
рендерити тільки напрямок і число. Хто має відрізняти «+100% від реальної бази» від
«+100% з нуля» — дивиться на `previous` сам.

**На співбесіді:**
> «Усі тренди й інсайти обчислюються з даних, тому цифри відрізняються від
> wireframe — там вони були плейсхолдерами, які між собою не сходились.»

## B9. Гроші

У макеті всі суми замасковані як `$1`. Реальні діапазони для seed:

| Що | Значення |
|---|---|
| Cross-Dock, сума ордера | $180 – $900 |
| Consolidation, сума ордера | $400 – $2 400 |
| Straps 12 (Securement) | $4.50 / шт |
| Corners 50 (Edge protect) | $1.20 / шт |
| Shrink wrap 120g (Wrap) | $18.00 / шт |

Тип у БД — `Decimal(12, 2)`, ніколи не `Float` (бо `0.1 + 0.2 !== 0.3`).
`lineTotal` і `subtotal` **не зберігаються** — обчислюються (`qty × unitPrice`),
щоб не було двох джерел правди.

## B10. Тижні для графіків

**Рішення:** ISO-тиждень (починається з понеділка). 10 бакетів: `W1` — найдавніший,
`W10` — поточний. Межі рахуються від сьогодні назад. У SQL — `date_trunc('week', closed_at)`.

**Саме так, без `AT TIME ZONE 'UTC'`.** `closedAt` — це `timestamp(3)` **без** таймзони, тож
`date_trunc` працює по збереженому UTC-годиннику й від таймзони сесії не залежить. Обгортка
`AT TIME ZONE 'UTC'` привела б колонку до `timestamptz`, а `date_trunc` над `timestamptz`
обрізає **в таймзоні сесії** — тобто вносила б рівно ту залежність, яку на вигляд прибирає
(ордер, закритий у понеділок 02:00 UTC, при не-UTC сесії впав би в попередній бакет, тоді як
`getWeekBucket` у Node поклав би його в поточний). Узгодженість «понеділок 00:00» між SQL і
`lib/week.ts` закріплена тестами в `week.test.ts`.

Перемикач `Day / CW / Month / Quarter` передається в API як `?granularity=`.
Реалізуємо `CW` (тиждень) як дефолт і `Month`; `Day` і `Quarter` — задизейблені
кнопки (див. лінію відсічення в PROGRESS.md).

# C. Технічні дрібниці, які легко зробити неправильно

| Питання | Рішення |
|---|---|
| Серіалізація `Decimal` | Мапиться в `number` у DTO-шарі. У компоненти `Decimal` не потрапляє ніколи |
| Дати | У БД — UTC. У API — ISO-string. Форматування тільки в `lib/format.ts` |
| Кешування | `export const dynamic = 'force-dynamic'` на всіх query-залежних роутах і сторінках зі `searchParams` |
| Пагінація | Offset (`skip`/`take`), `pageSize = 6` (як у макеті: `Showing 6 of 27`) |
| 404 | `notFound()` на сторінці, `404` + `{ error }` з API |
| Помилки API | `{ error: { code: string, message: string } }`, коди: `VALIDATION_ERROR`, `NOT_FOUND`, `INTERNAL_ERROR` |
| Пошук | Тільки по `Order.number` і `refNumber`, `mode: 'insensitive'`. Пошук по документах і інвойсах — out of scope |
| Вайлдкарди в пошуку | `contains` компілюється в `ILIKE '%…%'`, тому `%` і `_` з інпуту — це вайлдкарди, а не літерали (`?search=%` віддавав би всю базу). Екрануються в `lib/filters.ts::escapeLikeWildcards` |
| Сортування списку | `scheduledAt DESC, number DESC`. Другий ключ обов'язковий: `scheduledAt` не унікальний, а Postgres не гарантує порядку між рівними рядками — offset-пагінація без тайбрейкера дублює ордери між сторінками |
| Ізоляція серверного коду | `src/server/**` починається з `import "server-only"` — імпорт із `"use client"`-компонента падає на білді, а не тихо тягне Prisma в браузерний бандл |
| Кнопки без функціоналу | Рендеряться `disabled` з `title="Out of scope"`, а не імітують дію |
| Помилки | Кожен `catch` логує через `console.error` перед тим, як віддати `{ error }` — інакше 500 у проді не лишає нічого у Vercel-логах |
| CSV | Комірка з `"`/`,`/CR/LF береться в лапки; комірка, що починається з `=`, `+`, `-`, `@` — префіксується `'` (formula injection в Excel). Логіка чиста, в `lib/csv.ts`, покрита тестами |
